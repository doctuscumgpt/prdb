# Optimizer and Client Compilation Boundary

## Responsibilities and Isolation

Implement the optimizer in Rust and transform structured query requests into logical and physical plans. TinyCC produces the submitted C query library in the client using the prebuilt C SDK; the server optimizer does not compile that program. The executor's [SQL library](sql-library.md) owns SQL text parsing and operator execution; the planner validates its structured input, resolves authorized schema/types, and performs optimization. Run in a process separate from both the executor and storage manager: optimizer complexity, malformed inputs, and resource exhaustion must not compromise storage memory.

The planner is not an authorization authority. A compromised planner must not be able to mint execution grants or cause storage to release unauthorized values. Treat its plans as untrusted structured input. All client-built query artifacts are untrusted native code regardless of compiler or SDK provenance.

## Pipeline

```text
client: user C source + prebuilt C SDK -> TinyCC compiler/linker -> query.so
executor: query.so -> SDK SQL API -> structured planning request
optimizer: validated request -> logical plan -> physical plan
executor: SDK interpreter executes plan -> user code consumes results
```

The prebuilt SDK executes physical plans with an interpreter initially. There is no server compilation backend in the baseline; adding one requires an explicit future design decision.

Inputs are bounded structured requests from the executor, typed parameters as needed for planning, authorized schema, scoped estimates, and execution constraints. A provisioned submission channel binds requests to the existing execution context; input cannot change its identity or grant. Outputs require explicit versioning and validation. Plans carry logical relation/schema references, never optimizer-connection storage handles; the executor resolves them again through its scoped storage channel.

The bounded structured request header is `u16 version=1`, `u8 statement`, and `u8 flags=0`. The SELECT statement (`statement=1`) uses a single-relation record: schema and relation identifiers (`u8 byte_length` plus ASCII identifier bytes), `u16 projection_count` and that many identifiers, `u32 predicate_length` and prefix-encoded predicate bytes (zero length means absent), then `u8 limit_present` (0 or 1) and an optional `u32 limit`. Identifiers use `[A-Za-z_][A-Za-z0-9_]{0,62}`. There must be 1–128 projections. The full record is at most 64 KiB and predicate bytes at most 16 KiB.

The DELETE statement (`statement=2`) uses a separate bounded record: schema and relation identifiers, followed by a nonzero `u32 predicate_length` and one prefix-encoded predicate. It has no projection or limit fields; WHERE is mandatory. The Rust decoder enforces the same 64 KiB request, 16 KiB predicate, 256-node, depth-32, 4,096-byte text, and identifier bounds as SELECT. `bind_delete_request` and its invocation-metadata variant resolve only an authorized stable relation, require a Boolean predicate root, and produce no executor handle. `optimize_delete_v1` lowers a bound DELETE to the canonical kind-2 `Scan -> Filter -> Delete` plan. The optimizer process accepts distinct `optimize_select` (`0x1203`), `optimize_delete` (`0x1205`), and `optimize_update` (`0x1206`) IPC operations, routes each bounded request through authorized planner metadata, and validates all three canonical plan kinds in its response codec. ABI v5's operation-selected callback submits the bounded DELETE request on `OptimizeDelete`; the C SDK encodes the parsed SQL v1 DELETE AST, independently decodes the plan, matches its predicate columns and parameter values against the AST, then re-resolves the relation through executor storage before acquiring a normal relation handle. The SDK evaluates the matched predicate over authorized full-scan batches, polls cancellation, and stages matching row handles through ordinary executor mutation IPC. The maintained confined acceptance exercises optimizer-backed DELETE and verifies the rows are absent before durable commit. Confined cancellation and injected-failure coverage for DELETE remain open.

The UPDATE statement (`statement=3`) uses schema and relation identifiers, a `u16 assignment_count` (1–64), then assignments in source order. Each assignment is a column identifier followed by kind `0` and a nonzero one-based `u32` parameter index, or kind `1` for NULL. A nonzero `u32 predicate_length` and one bounded prefix predicate follow; WHERE is mandatory. The Rust request decoder enforces the 64 KiB request, 16 KiB predicate, 256-node, depth-32, 4,096-byte text, 63-byte identifier, 64-assignment, and parameter-index bounds. Invocation-bound binding resolves assignment and predicate columns against authorized relation metadata, rejects unknown or duplicate target columns and NULL assigned to non-nullable columns, and requires a Boolean WHERE root. Binding does not confer write authority. The `optimize_update` process operation (`0x1206`) composes authorized relation lookup and canonical kind-3 plan output. The C SDK independently decodes and validates UPDATE assignments, predicate references, exact scan shape, target uniqueness, parameter bounds, and NULLability. `prdb_sdk_optimizer_encode_update_v1` serializes the parsed UPDATE AST into the bounded request, and `prdb_sdk_optimizer_submit_update_v1` submits it through ABI v5's operation-selected callback. `prdb_sdk_optimizer_validate_update_plan_with_parameters_v1` matches the returned predicate and source-order assignments against the AST, checks exact scalar type codes and NULLability, and re-resolves the plan relation through executor storage. `prdb_sdk_optimizer_execute_update_ast_v1` scans authorized full-shape batches, evaluates the AST predicate, collects row handles, closes the scan, and stages the verified parameter/NULL patches through ordinary executor mutation IPC. The confined `sandboxed_v3_sql_dml_sequence_is_visible_and_commits` acceptance covers parameterized single-column and NULL assignments and multi-column value visibility through authenticated optimizer/executor processes and durable commit. Its denied-write case verifies that an otherwise valid plan reaches storage, receives an authorization rejection for a readable table without UPDATE grant, and ends in a durable `QueryError` abort, and leaves the committed row unchanged. The TinyCC SDK suite also verifies cancellation cleanup, optimizer callback failure, stage-update failure, and target-capacity failure without publishing mutation counts on error. Confined cancellation and explicit staging-failure injection, plus broader transaction conflict/policy acceptance, remain open.

The composite join SELECT request (`statement=4`) uses the same version-1 four-byte request header, then schema, left-relation, and right-relation identifiers; `u16 projection_count` (1–128) followed by `(u8 relation_side, identifier)` records where side is 0 for left and 1 for right; `u8 join_key_count` (2–8) followed by left/right identifier pairs; and `u8 limit_present` plus an optional `u32 limit`. The decoder rejects invalid sides, out-of-range counts, malformed identifiers, truncated fields, and trailing bytes within the existing 64 KiB request cap. The invocation-bound binder resolves both names independently through authorized planner metadata, requires the same schema ID/version, binds projections and key sides to stable column IDs/ordinals, and rejects incompatible key types before planning. Decimal key scales must match; differing Decimal precision is allowed. The optimizer process routes operation `optimize_join_select` (`0x1207`) through two authorized plan-relation lookups with distinct request IDs in a namespace disjoint from direct planner SDK calls. It returns plan v1 kind 4: common schema identity, two relation name/ID/epoch references, each side's unique ordinal-sorted scan-column shape, ordered side-qualified projections, 2–8 bound equality-key pairs, and an optional limit. Rust and the TinyCC C SDK independently validate both scan shapes, projection/key membership, relation/schema identity, key type compatibility, collection bounds, version, and trailing bytes. The C SDK serializes the parsed alias-aware v19 INNER JOIN AST to statement 4 and submits it with operation `0x1207` through ABI v5. It also checks the returned schema/relation names, projection sides/order/types, composite keys, and LIMIT against the parsed and bound AST. Before execution, it re-resolves both relation references through executor storage and compares stable IDs, epochs, and every scanned column definition. The optimizer-backed v19 SDK entry point then executes the matching bounded join operators only after all checks succeed. The two-key aliased join passes through the confined ABI v5 SQL artifact acceptance, result relay, and durable commit. This remains the unfiltered request subset; planning/execution measurements remain open.

The first grouped optimizer subset is the single-key COUNT request (`statement=5`): schema, relation, group-key identifiers, then an optional `u32 LIMIT`. Rust binds the key to invocation-authorized metadata and returns kind 5 containing the stable relation reference and exact one-column scan shape. It supports `SELECT key, COUNT(*) FROM relation GROUP BY key [LIMIT n]`; WHERE, HAVING, ORDER BY, composite keys, and other aggregates are outside this request. The TinyCC SDK independently decodes kind 5, encodes this v4 AST shape, and submits it through ABI v5 operation `0x1208`. Before execution, the SDK matches relation/schema, projected and grouped key bindings, and LIMIT against the parsed statement, then re-resolves the relation and exact scan-column identity through executor storage. The optimizer-gated v4 runner executes only after those checks, using the authorized bounded scan and existing COUNT grouping kernel. The confined ABI v5 SQL fixture exercises this path through result relay and durable commit. Kind 5 remains unordered; single-key COUNT ordering is provided by the separate statement-8/kind-8 subset. HAVING, composite grouped ordering, additional optimizer aggregate types, and analytical workload measurements remain open.

The composite COUNT request subset (`statement=6`, using the existing `OptimizeGroupCount` operation) adds two to eight projected/grouped keys and optional post-group LIMIT, with no WHERE, HAVING, or ORDER BY. Rust bounds and decodes the request, resolves every key through authorized relation metadata, rejects duplicate bound ordinals, preserves SQL key order, and returns canonical kind 6 with the exact unique ordinal-sorted scan shape. TinyCC encodes the v13 AST, independently decodes kind 6, checks every key against the parsed and authorized binding, and re-resolves the relation and exact scan shape through executor storage before calling the existing authorized composite grouping runner. The confined ABI v5 SQL fixture exercises two-key COUNT through operation `0x1208` and verifies the relayed SQLR rows through durable commit. Request bounds/trailing-byte, binding duplicate/order, canonical plan, process-channel, TinyCC decode/matching, and confined acceptance checks pass. Composite-group ordering and analytical workload measurements remain open.

The ordered SELECT request (`statement=7`, routed through `OptimizeSelect` `0x1203`) extends the explicit-projection single-relation form with the order-key identifier, a descending flag, and an optional `u32 LIMIT`. The Rust optimizer resolves the key through invocation-authorized metadata and emits canonical plan kind 7: stable schema/relation identity, the ordinal-sorted union of projected columns and the possibly hidden order key, source-order projections, key direction, and LIMIT. The C SDK independently decodes the plan, matches relation/projection/order/LIMIT to the SQL v3 AST, and re-resolves the relation and scan shape through executor storage before scanning. Execution is bounded to 128 rows and 1 MiB, stable-sorts by the authorized typed key, applies LIMIT after sorting, and polls cancellation before sorting and during publication. The maintained confined SQL artifact verifies descending hidden-key output through result relay and durable commit. This does not change the unordered semantics of statements 5 and 6; grouped ordering uses the separate statement-8/kind-8 request and plan described below. Composite-group sorting and analytical/mixed-workload measurements remain open.

Grouped COUNT sorting uses request statement 8 and plan kind 8 under the existing `OptimizeGroupCount` operation. The bounded request contains schema, relation, and one group-key identifier, then a sort-item count (1–2), followed by each item's source (`0` group key or `1` COUNT(*)), descending flag, and NULLS FIRST flag, then the optional LIMIT. Repeated sort sources, invalid flags, extra bytes, WHERE, HAVING, composite grouping, and aggregates other than COUNT(*) are rejected. The authorized binder resolves the group key and emits kind 8 with the stable relation reference, exact one-column scan shape, group key, the ordered sort items, and optional LIMIT. The TinyCC SDK independently checks the plan against the parsed v12 AST and authorized binding, re-resolves executor identity, and only then runs the bounded grouped COUNT operator. Sorting is stable, applies NULL placement and direction per item, and applies LIMIT after sorting under the existing 128-group/1 MiB materialization budget. Statement 5/kind 5 and statement 6/kind 6 retain their existing unordered meanings. Confined acceptance must verify ordered SQLR output through result relay and durable commit. Composite-group sorting and analytical/mixed-workload measurements remain open.

Composite grouped COUNT sorting uses request statement 9 and plan kind 9 under `OptimizeGroupCount`. The request encodes schema/relation, two to eight group-key identifiers in SQL order, one to nine unique ORDER BY sources selected from those keys or COUNT(*), each source's group-key index when applicable, direction, NULL placement, and optional LIMIT. WHERE, HAVING, other aggregates, repeated or unselected sort sources, malformed flags, and trailing bytes are rejected. The kind-9 plan carries the stable relation reference, exact ordinal-sorted group-key scan shape, group keys in SQL order, sort sources in SQL order, and LIMIT. The TinyCC SDK independently matches the plan to the parsed v15 AST and authorized binding, re-resolves executor identity, then invokes the bounded v15 grouped sort runner. It retains stable lexicographic ties, NULL placement/direction per item, and LIMIT-after-sort behavior under the existing 128-group/1 MiB cap. Statement 6/kind 6 remains unordered. Composite-order optimizer acceptance must verify exact SQLR output through result relay and durable commit.

Predicate node tags are `0x00` NULL; `0x01` Boolean followed by 0 or 1; `0x02` signed big-endian i64; `0x03` UTF-8 text with a big-endian u16 byte length (at most 4,096 bytes); `0x10` column identifier; `0x20` comparison followed by operator byte (0 equal, 1 not-equal, 2 less, 3 less-or-equal, 4 greater, 5 greater-or-equal) and two child nodes; `0x30` AND and `0x31` OR followed by a child count (2–16) and those child nodes; `0x32` NOT followed by one child. Predicates are bounded to 256 nodes and depth 32. Unknown tags, invalid values, truncation, and trailing bytes are rejected. The decoders check structure and resource bounds; the binder resolves relation/column names, infers expression types, and produces a canonical plan, while storage remains responsible for authorization and writes. Unsupported literal types and statement kinds without a defined request record are rejected in v1.

The in-process v1 binder's `bind_select_request_via_metadata` entry point resolves the request's exact qualified name through `PlannerMetadataConnection` on the admitted invocation before binding. A missing description and a description whose relation name does not match the requested name produce the same `RelationUnavailable` result. It binds the request to pinned schema ID/version, table ID/write epoch, and column IDs/ordinals/types/nullability; duplicate or malformed catalog metadata fails closed. Comparisons require matching known scalar types (or a NULL operand), and Boolean operators require Boolean expressions. The bound result retains the resolved schema/relation names plus stable catalog identities. This helper does not select a physical access path or create an executor grant. Planner IPC `describe_plan_relation` (`0x1204`) and executor IPC `resolve_plan_relation` (`0x1105`) return the same authorized stable identity without minting a handle. The executor-side endpoint lets the SQL library re-resolve a decoded plan against the same invocation snapshot before obtaining a scan capability.

The initial plan builder, `plan_select_v1`, lowers this bound SELECT to a linear `Scan -> Filter? -> Project -> Limit?` pipeline. The scan column set is the unique ordinal-sorted union of projected and predicate columns; projection order and duplicates remain intact. Every relation and column reference carries stable catalog IDs, schema version, and table write epoch, never a planner handle or permission. `validate_plan_v1` independently checks pipeline order, reference membership, Boolean filter types, duplicate/missing columns, and predicate bounds.

The mutation-plan format defines canonical DELETE plan v1 with kind 2 and `Scan -> Filter -> Delete` (node tags 1, 2, 5), and UPDATE plan v1 with kind 3 and `Scan -> Filter -> Update` (node tags 1, 2, 6). DELETE carries the unique ordinal-sorted predicate scan shape and its Boolean predicate. UPDATE carries the unique ordinal-sorted union of assignment targets and predicate references, a Boolean predicate, then 1–64 assignments in source order. Each UPDATE assignment contains a complete bound column record and a fixed value record: kind 0 plus a nonzero one-based parameter index, or kind 1 plus a zero parameter index for NULL. The Rust plan validators check relation identity fields, scan and predicate references, Boolean result type, assignment uniqueness, parameter bounds, NULLability, and predicate budgets. The C SDK independently checks UPDATE predicate and assignment structure, exact scan shape, assignment uniqueness, parameter bounds, and NULLability before relation validation. Plans carry no row handles, permissions, or write grants. The DELETE path includes bounded request/binding, canonical plan construction, optimizer-process IPC, independent C decoding, AST matching, executor relation re-resolution, authorized scan, ordinary stage-delete execution, and confined durable acceptance. The UPDATE path includes bounded request/binding, canonical plan construction, optimizer-process IPC, independent C decoding and AST assignment/predicate checks, executor relation re-resolution, authorized scan, ordinary stage-update execution, bounded failure handling, and confined parameterized/NULL/multi-column acceptance. Confined failure injection and broader transaction conflict/policy acceptance remain open.

`encode_plan_v1` and `decode_plan_v1` implement the canonical version-1 SELECT plan payload (maximum 64 KiB). Its header is `u16 version=1`, `u8 kind=1` (SELECT), and `u8 reserved=0`, followed by schema name (`u8 length` and ASCII identifier), schema ID[16], schema version `u64`, relation name (`u8 length` and identifier), relation ID[16], table write epoch `u64`, and a `u8` node count (2–4). Node tags are `1` Scan (`u16` scan-column count and full column records), `2` Filter (one prefix predicate), `3` Project (`u16` projection count and full column records), and `4` Limit (`u32` row count). A column record is ID[16], ordinal `u32`, scalar type code `u8`, type parameters[4], and nullable `u8`. Type codes 1–11 and parameters match the IPC relation-description encoding. Scan columns are limited to 256 and projections to 128. Filter predicates use the request v1 node tags, except a column node carries its bound column ID[16] rather than a name. The Rust decoder resolves those IDs only against the preceding scan shape and runs the independent plan validator. `optimizer_service::optimize_select_v1` composes request binding, conservative lowering, and canonical plan encoding against an invocation-bound `PlannerMetadataConnection`; a real-redb test checks the result against pinned catalog identities. The `optimize_select` (`0x1203`), `optimize_delete` (`0x1205`), and `optimize_update` (`0x1206`) IPC operations and `OptimizerSubmission` role have generated constants and allowlists. The `prdb-optimizer` executable serves all three operations in a separate process, requests stable authorized relation metadata through `describe_plan_relation` (`0x1204`), and returns a validated kind-1, kind-2, or kind-3 plan or non-disclosing status. The supervisor launcher starts the optimizer beside the executor in the invocation cgroup, gives it separate submission and planner Unix sockets, and serves both planner streams concurrently with the executor's planner stream. The optimizer receives its own Landlock policy and seccomp filter. ABI v4 exposes a fixed-operation executor callback for bounded SELECT submissions; ABI v5 adds an operation-selected callback for bounded SELECT/DELETE/UPDATE submissions under the same trusted role allowlist. The C SDK's `prdb_sdk_optimizer_encode_select_v1` serializes an explicit-column single-relation SQL v2 AST, a caller-supplied schema identifier, and optional LIMIT into request v1, with no WHERE tree. `prdb_sdk_optimizer_encode_select_with_parameters_v1` additionally serializes supported parameterized comparisons and Boolean AND/OR/NOT trees using the request v1 bounded prefix format. It supports Boolean, INTEGER, TEXT, and NULL parameter values; IS [NOT] NULL, SELECT *, and other value types remain unsupported and stay on the established SQL execution path. `prdb_sdk_optimizer_decode_plan_v1` validates the `Scan -> Project -> optional Limit` subset. `prdb_sdk_optimizer_decode_plan_with_filter_v1` validates the complete v1 pipeline, including its bounded predicate tree, scanned column references, scalar compatibility, and Boolean root. Both reject malformed identities, types, order, references, lengths, and trailing bytes. Plan names and the validated prefix predicate borrow the complete payload. `prdb_sdk_optimizer_validate_executor_relation_v1` independently decodes a plan, asks executor storage to re-resolve it with `resolve_plan_relation` (`0x1105`), and compares stable identities and scanned columns. `prdb_sdk_optimizer_acquire_plan_relation_v1` obtains a normal executor relation handle only after that validation and checks its relation ID/name. `prdb_sdk_optimizer_open_plan_scan_v1` opens a full scan from the checked handle and skips cursor creation for `LIMIT 0`. The plan batch consumer evaluates the validated Filter prefix tree against scanned cells with SQL three-valued comparisons before projection; false and UNKNOWN rows do not count toward LIMIT. The bounded runner polls cancellation between pages, caps scan execution at 125 pages so plan comparison, cancellation, batch, setup and cursor-close calls fit the 256-request executor stream budget, honors LIMIT, and closes early cursors. The SQL SDK path submits parsed SELECT ASTs over ABI v4 and verifies returned relation, projections, LIMIT, Filter operators, predicate columns, and parameter values against the AST and executor-authorized metadata before executing. The parameterized bridge supports bounded comparisons and Boolean AND/OR/NOT with Boolean, INTEGER, TEXT, and NULL parameters; unsupported forms return to the established SQL path. `prdb_sdk_optimizer_execute_select_ast_to_result_v1` and its parameterized counterpart write each projected row as a provisional SQLR v1 record through the host result callback.

## Storage and Statistics Access

Use a dedicated planning channel for authorized schema, logical access paths, and bounded estimation requests. This is a richer interface than the worker scan API but grants no broader data authority. The storage-owned [statistics service](statistics-service.md) performs collection and policy-aware estimation; the optimizer consumes results and compares candidate plans.

Request cardinality, authorized output size, selectivity, and eventually distinct-count/correlation estimates as supported. Each estimate identifies its population and uncertainty. A readable-cell estimate cannot substitute for an estimate over every visible row. An estimate never proves a query is authorized.

The planner cannot request unrestricted refresh jobs, access raw global catalogs, or submit native estimation callbacks. Each planner stream has a cumulative allowance of 16 storage estimate requests; once exhausted, storage returns `Unknown` and planning may continue with fixed heuristics. This estimate allowance is separate from the existing 256-request planner stream cap and the invocation deadline. Exhaustion of the overall planning budget, cancellation, or deadline expiry terminates planning. Treat all returned metadata as potentially disclosed through plans, diagnostics, and executor output.

## Catalog and DDL Boundaries

Use only authorized catalog names/types and logical access paths from the pinned schema. Administrative DDL bypasses query optimization and goes to the validated control path; the optimizer cannot create tables, indexes, users, or policies. Plans bind stable catalog IDs and schema epochs. A published index is an optional storage access path, never a bypass for row/cell policies or version visibility.

Metadata binding also supports the fixed virtual relations in [metadata discovery](metadata-discovery.md). Their estimates and scans use filtered metadata only. The optimizer cannot inspect raw catalog records, physical roots, live cross-user registries, or privileged expression definitions. Cache validity follows [data dictionary](data-dictionary.md), including checks independent of notification delivery.

## Concurrent and Writable Plans

Produce read and mutation plans for the initial SQL subset. Plans contain logical targets and supported expressions, never permissions or commit decisions. Storage checks every staged mutation and commit independently. Plan input and estimates use the invocation snapshot plus its current private writes, identified by a transaction-local write generation. Replan/re-estimate after generation changes; no stale plan estimate can establish authorization.

Use bounded optimizer queues across invocations. A single invocation initially has one active planning/statement stream. Internal statistics requests must hold storage-owned snapshot pins until completion even if the executor exits. Do not let planner completion race transaction closure or change the invocation snapshot.

## Workload Priorities

Follow [workload profile](workload-profile.md): prioritize point/range access and predictable operational latency on the row store. The analytical follow-on chooses bounded join/group/sort plans over authorized batches and scoped estimates. Avoid unbounded optimization effort for small transactions. Planner estimates cannot authorize hidden-key index probes or hidden-data aggregation. Resource class and budgets are supplied by admission, not enlarged by plan output.

## Optimization Constraints

Optimize the authorized view. Never push a hidden-value predicate, user function, or native callback ahead of authorization. Storage must independently validate any requested pushdown. Error behavior for redacted inputs is part of semantics and must be preserved by rewrites.

Global histograms, samples, counts, and private-data-derived cost estimates are unavailable to the planner. Use scoped authorized-view summaries or conservative heuristics. Shared plan caches must not cross permission boundaries or reveal protected metadata. Historical estimates must remain valid for the current authorization and snapshot; staleness is not solely a performance issue.

## Native Artifacts and Budgets

User query artifacts are compiled in the client and loaded only in confined executors. The [SDK specification](client-sdk.md) defines packaging and version checks. Keep native ABI and IPC versions separate. Native SQL-plan generation by the server is outside the baseline and would require a separate design decision.

Bound server planning independently from execution and statistics estimation. Client compilation has its own latency and resource profile. A planning failure returns a bounded error and releases temporary resources; it must not fall back to executing user code inside storage.

## Validation and Limits

Test malformed queries, resource exhaustion, invalid output, unauthorized metadata requests, estimation probes, heuristic fallback, and rewrites involving redacted inputs. Compare SDK SQL execution with reference results on authorized data. Verify that changing only inaccessible data does not change released estimate content for a fixed authorized view.

Isolation protects data boundaries, not semantic correctness. Whether generated plans are trusted for correct results or require additional validation remains a separate research decision.
