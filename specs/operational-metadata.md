# Operational Metadata, Monitoring, and Diagnostics

## Consistency and Access

Operational state is live, not part of the invocation's repeatable MVCC data snapshot. Expose it through authenticated control APIs, not normal executor SQL or `information_schema`. Each response includes an observation time and consistency label; a bounded snapshot of one registry is not a transactionally consistent snapshot of all processes.

An authenticated user may inspect status for their own invocations. Database administrators may inspect global registries and request administrative cancellation. Object-level DDL privileges do not imply access to other users' queries, credentials, or global workload statistics. A delegated monitoring role can be designed later; the initial global privilege is reserved database administration.

## Registries

| Surface | Example fields | Persistence / exposure |
| --- | --- | --- |
| Invocations | Opaque ID, owner, workload class, ACTIVE/COMMITTING/terminal state, start/deadline, cancellation state, budget usage | Live registry plus durable final outcome; own or administrator |
| Storage transactions | Internal transaction ID, state, write-set bytes, age, pin count | Administrator only; IDs/epochs never leaked through optimizer APIs |
| Waits/fences | DDL fence wait category, duration, opaque wait/resource/blocker IDs | Administrator-only best-effort page snapshot; no raw addresses or object names to owners |
| Jobs (future) | Type, owner/controller, queued/running/completed/failed, bounded progress, failure category | No asynchronous job API is implemented; add a runtime registry only with a supported background job |
| Memory/history | Queue usage, pinned history, cache size, oldest-pin age | Global administrator summaries, not per-query private-data estimates |
| Counters | Admissions, conflicts, policy denials, cancellations, bytes, latency buckets | Administrator aggregates; own-invocation usage is limited to that invocation |

Do not include query text, SQL parameters, native source, row values, token secrets/verifiers, filesystem paths, or arbitrary exception dumps by default. Diagnostics containing object names require authority to see those objects. Even aggregate global metrics reveal workload and data-volume information, so ordinary users and the optimizer do not receive them.

The current engine has no asynchronous maintenance-job API. DDL and index builds run synchronously as authenticated control operations. redb compaction runs through `prdb-maintain compact` after services stop and the exclusive instance lock is acquired; it is not a queued supervisor job. Do not expose an empty or synthetic job registry, and do not add engine checkpoint jobs because redb owns physical persistence and recovery. Define job states, progress, retention, and recovery markers when a supported asynchronous operation is introduced.

## APIs and Ordering

```text
get_invocation_status(invocation_id) -> authorized_status
list_own_invocations(page_limit, continuation?) -> page
admin_list_runtime(kind, page_limit, continuation?) -> page
cancel_invocation(invocation_id, reason_code) -> accepted_or_terminal
```

Authenticate and authorize every control call against current state. Use bounded pages/cursors and opaque identifiers. Recheck authority between pages; fail if a cursor expires or privilege changes. Runtime pages may show changes between reads and must not expose a global total to a caller limited to their own invocations. Define registry-generation tokens for coherent pagination where supported; otherwise explicitly mark best-effort enumeration.

`StorageManager::get_invocation_status` provides owner-scoped point status. It returns ACTIVE or COMMITTING from the in-process registry, then falls back to an unexpired durable outcome after the invocation leaves that registry or after restart. Cross-owner, unknown, and expired IDs all return absence. `StorageManager::list_own_invocations` returns only the authenticated owner's current live entries in invocation-ID order; terminal entries remain available through point status. Pages contain at most 128 entries and include the caller-supplied trusted observation time and a best-effort consistency label. A continuation is bound to its owner and owner-registry generation. A change to that owner's live entries or phases invalidates it, so callers restart enumeration on a stale-cursor error; changes to other owners' entries do not invalidate it. `StorageManager::list_runtime_invocations` returns bounded live invocation pages only after revalidating current database-administrator authority on every call. Each administrator record includes an opaque transaction ID, its invocation's `operational` or `analytical` workload class and state, age at the observation time, current staged row count and staged row-payload bytes, and snapshot pin count (0 or 1 redb read snapshot retained by that invocation). Transaction IDs are random nonzero values unique among concurrent live transactions and are not optimizer identifiers. The payload-byte count excludes row IDs and index metadata. A write-set or transaction admission/release update invalidates administrator continuations so later pages do not silently span different registry usage. It returns no global count, and any runtime registry change invalidates its administrator-bound continuation. `StorageManager::cancel_invocation` also requires current database-administrator authority and a nonzero reason code. It durably records an AUD1 administrative-cancellation event before accepting the request, then publishes the reason in the process-local registry. A pending audit decision blocks that invocation from entering COMMITTING; audit failure clears the pending request. Owner status shows a cancellation-requested flag, while administrator pages also return the reason code. Requests are limited to 30 per actor per rolling minute by default. The registry is process-local, shared by live manager handles for the same redb `Database` object, and bounded by the active-invocation cap. Other runtime kinds still require the authenticated control service.

The same administrator runtime page carries a best-effort snapshot of active DDL fence waits. The process-local fence manager tracks at most 128 waiters and rejects additional blocked acquisitions; a blocked request can reference at most 128 tables, while immediately granted requests have no added resource-count limit. Each page returns at most 16 waits, with up to eight opaque table resource IDs and eight blocking lease/wait IDs per entry; explicit flags mark each shortened list and whether wait entries were omitted. A wait record disappears when its request acquires the fence or times out. The wait snapshot is sampled independently on every runtime page and is not pinned by an invocation cursor. It exposes no table names, pointers, or raw addresses.

The administrator runtime page also reports a best-effort pinned-history summary: the number of live invocation snapshots currently held and the age of the oldest such pin at observation. These values are sampled independently from page records and are not retained by cursors. They describe redb read-transaction pins only; this summary does not estimate retained page bytes, cache size, or total memory. `invocations_admitted_total` counts successful admissions in the current process-local registry, saturates at `u64::MAX`, and resets when that registry is recreated, including after restart or when its last manager handle is dropped. `invocation_conflicts_total` counts invocation commits rejected with `CommitError::Conflict` under the same saturation and registry-reset rules. `admin_cancellations_accepted_total` counts first transitions to cancellation-requested after the required accepted audit record is durably committed; denied and repeated accepted requests do not increment it. `admin_cancellations_denied_total` counts only cancellation requests whose `Denied` AUD1 record is durably committed; unauthorized and rate-limited calls and any request whose audit commit fails do not increment it. `invocation_policy_denials_total` counts managed invocation executor IPC requests that return explicit `AuthorizationError::Denied`; each rejected request is counted once. Hidden rows/cells, unavailable relations, malformed requests, and policy evaluation failures are not counted as denials. `invocation_staged_value_bytes_total` adds the encoded payload length of each successful managed-invocation overlay put, including replacements; deletes and failed writes add nothing. It measures cumulative accepted staging volume, while each live record’s `staged_value_bytes` remains the current write-set size. `invocation_commit_latency_buckets` is a six-element array of noncumulative counts for managed `InvocationTransaction::commit` calls, including both success and error results, measured from API entry until return using a monotonic clock. Its ordered ranges are `<=1,000us`, `(1,000us,5,000us]`, `(5,000us,10,000us]`, `(10,000us,50,000us]`, `(50,000us,100,000us]`, and `>100,000us`. Uncoordinated transactions are excluded. Bucket counts saturate at `u64::MAX` and reset with the process-local registry. All counters saturate and reset with the process-local registry. These are global administrator-only counters, not durable lifetime totals. Other wait categories and registry families remain unimplemented.

Runtime page version 3 adds `redb_cache_used_bytes`, sampled from the pinned redb 4.4 cache metrics API. It reports bytes currently held by redb's page cache, not process RSS or total memory. This value is separate from the invocation records, is not bound to the continuation cursor, and reveals no row or key contents. Older operation versions retain their existing response shape. redb's allocated/stored/metadata/fragmented page statistics require a write transaction in this release; the engine does not acquire the writer solely for monitoring because that could delay commits. Exact retained-history bytes remain unavailable.

The same page reports `outcome_maintenance_passes_total`, `outcome_maintenance_failures_total`, and `outcomes_pruned_total` for bounded durable-outcome pruning calls made through this storage-manager process. A pass counts each call whether it succeeds or fails; failures count calls that return a maintenance error; removed outcomes count only successful calls and add the reported removal count. These process-local counters saturate at `u64::MAX` and reset with the registry. They do not expose failure details or persistent outcome contents.

An accepted cancellation is not proof of rollback. The registry serializes cancellation acceptance with the transition into COMMITTING: if cancellation wins, finalization records ABORTED and publishes no writes; if COMMITTING wins, cancellation is denied as too late or returns the already established terminal outcome. A COMMITTED outcome remains committed even if result delivery, executor exit, or telemetry collection fails. Registry absence after restart is not ABORTED: consult the [durable outcome store](physical-metadata.md), and return UNKNOWN/EXPIRED when the retained record cannot establish a result.

## Audit Events

Record administrative DDL, membership/grant/policy changes, token lifecycle operations, authentication failures, and administrative cancellation with actor/target IDs, bounded action/result codes, and correlation IDs. Do not log credential secrets, query contents, row values, or hidden constraint keys. A successful administrative state change must have its audit record or audit outbox entry included in the same durable commit; external log delivery may follow asynchronously.

### AUD1 Payload v1

The initial `audit_v1` value is a fixed header followed by target IDs: ASCII `AUD1`; little-endian u16 version `1`; little-endian u16 action code; little-endian u16 result code; little-endian u16 target count; 16-byte nonzero event ID; 16-byte actor ID (all zero means authentication did not produce a principal); 16-byte nonzero correlation ID; signed little-endian i64 UTC microseconds; then exactly `target_count` raw 16-byte nonzero target IDs in strict unsigned-byte order. The redb key is the 16-byte event ID and must match the value. The fixed header is 68 bytes; target count is at most 256 and total payload at most 4,164 bytes. Duplicate or unsorted targets, unknown codes, zero required IDs, nonpositive timestamps, and any non-exact length fail closed. Action codes are DDL=1, authority change=2, token lifecycle=3, authentication failure=4, administrative cancellation=5. Result codes are succeeded=1, denied=2, failed=3, accepted=4. This envelope deliberately contains no query text, credential material, row values, or arbitrary diagnostic text.

Keep audit storage separate from ordinary catalogs and data reads. Only database administrators can inspect it initially. `audit.events.list` returns an exclusive event-ID ordered page, with a caller-selected limit from 1 through 128 and a cursor bound to the administrator ID. It revalidates current database-administrator authority on every request. Pages are best-effort across independent redb snapshots; newly appended events can appear in later pages when their random IDs sort after the cursor, and older IDs inserted before it are not included. A cursor contains no event contents. The projection contains only AUD1 event ID, optional actor ID, correlation ID, UTC microseconds, action/result codes, and target IDs; it never returns encoded bytes, arbitrary diagnostics, query contents, credential material, or row values. A key/value ID mismatch or malformed AUD1 record fails the page closed. Failed token authentication writes a denied `AuthenticationFailure` event with no actor ID and the nonzero attempted token ID as its sole target; zero token IDs have no targets. At most four such records per token ID per rolling minute are persisted, with at most 4,096 token IDs tracked by a live storage-manager limiter. Further failures remain authentication denials but are not individually audited. The table accepts at most 16,384 events, bounding raw AUD1 payload storage to approximately 65 MiB before redb overhead. Online writes never delete events. At capacity, audit-required state changes and audit writes fail closed with an explicit capacity error; existing history remains inspectable. An operator can reclaim capacity with the offline `prdb-maintain audit-archive` command after stopping the gateway and supervisor. The command requires the exclusive instance lock, writes a private archive outside the instance directory, syncs the archive and its parent directory, and only then deletes the exact archived events in one redb transaction. It never overwrites an archive; if an earlier run stopped after publishing a matching archive but before pruning redb, rerunning with the same path verifies the archive and completes pruning. Invalid or mismatched archives leave the audit table unchanged. If a required administrative audit record cannot be committed, fail that administrative action; do not claim the action was audited. Routine metrics failure must not convert committed database writes into reported aborts.

### PRA1 Offline Audit Archive v1

The offline archive is a single checksummed byte stream: ASCII `PRA1`; little-endian u16 version `1`; little-endian u64 event count; then records sorted by event ID, each containing the 16-byte redb event key, little-endian u32 AUD1 payload length, and the exact AUD1 payload; finally, a 32-byte SHA-256 digest of all preceding archive bytes. Each record must decode as AUD1 and its key must match its embedded event ID. Version 1 accepts at most 16,384 events and at most 4,164 payload bytes per event. The archive is mode `0600` and outside the instance directory. The destination must be absent, or an existing mode-0600 regular file containing the exact same archive so an interrupted prune can be retried. The operation never replaces existing files. `prdb-maintain audit-verify --archive PATH` independently checks the file type, permissions, size, checksum, record ordering, and every AUD1 payload without opening a database. PRA1 is not encrypted or keyed and therefore detects accidental corruption, not malicious rewriting.

### Optional JSONL Audit Sink

The supervisor optionally delivers retained AUD1 records when `PRDB_AUDIT_JSONL_PATH` names an absolute local sink path. It scans the durable AUDIT outbox in event-ID order at one-second intervals and attempts batches of at most 64 records. A sink error is ignored by the request/result path; the AUDIT event remains durable and pending for a later retry. The sink parent directory must already exist. The sink must be a regular, single-link file with mode `0600`; new files are created with that mode and without following symlinks. The supervisor takes a nonblocking exclusive file lock while repairing/appending, writes one bounded JSON object per line, and syncs each line before committing its delivered marker in `STATS`. A partial final line left by a crash is truncated before retry. This is at-least-once delivery: a crash after file sync and before marker commit can repeat the line. Consumers deduplicate by the lowercase hexadecimal `event_id` field. The JSON projection contains event, actor, correlation and target IDs, UTC microseconds, and numeric action/result codes; it excludes arbitrary text and secrets. Changing the configured canonical path or replacing its file identity (path, device, inode, and birth timestamp) resets delivery markers and replays retained AUDIT history. A filesystem that does not report a file birth timestamp cannot be used for this sink. Markers for offline-pruned events are removed in the same redb transaction that prunes those AUDIT rows. Operators using the systemd Landlock units must allow the configured sink path for supervisor writes. This local file sink is optional; it is not tamper-proof against an administrator controlling the host or database files.

Audit is not tamper-proof against an administrator controlling database files; external tamper-evident collection is a future feature. Do not retain plaintext tokens to improve debugging or recovery.

## Resource Safety and Tests

Monitoring must not hold commit/catalog locks while formatting or waiting for a client. Use bounded copies or pinned registry snapshots and release references promptly. Telemetry observers cannot pin data history indefinitely or bypass queue/admission budgets. Separate required commit/outcome bookkeeping from optional high-volume metrics.

Test cross-user status denial, unknown IDs, revocation mid-page, commit/cancel races, restart with committed-but-undelivered results, retention expiry, high-volume denied requests, audit sink failure, partial registry snapshots, and the absence of secrets in every error/log path. No SQL-visible live system views are promised in the initial implementation.
