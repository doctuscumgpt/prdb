# Catalog Bootstrap, Versions, and Upgrades

## Bootstrap Without SQL Dependencies

The Rust engine contains a minimal, versioned bootstrap descriptor for system record types, reserved IDs, primitive encodings, and required catalog indexes. This descriptor is sufficient to read the catalog root and authenticate startup; it does not depend on querying SQL, user-defined policies, or loading the C SDK.

Initialization requires exclusive ownership of an empty explicitly selected data directory. Never initialize over an existing, corrupt, or unknown-format database. Acquire the instance lock, create private temporary files, and write a database UUID, format metadata, built-in type/schema/object records, reserved administrative role, and initial identity through the normal durable machinery.

Reserve internal catalog and `information_schema` namespaces. No user statements can replace them. A catalog may describe its own built-ins for inspection, but engine bootstrap descriptors remain the authoritative decoder for its format; self-description cannot redefine how arbitrary bytes are interpreted.

## Initialization and Credential Handoff

Use `UNINITIALIZED -> INITIALIZING -> READY` state recorded durably in engine metadata. Bind bootstrap to the local permission-restricted setup owner. Do not expose ordinary query or administrative listeners while initializing. Publish READY only after redb opens/recoveries successfully, mandatory catalog integrity checks pass, and bootstrap credential handoff completes.

Generate the first token in trusted code, store its verifier only, and deliver the secret once over the protected setup connection. If delivery/acknowledgement is lost, resume setup under the same exclusive local ownership, revoke the unclaimed token, and issue a replacement; never recover plaintext from storage or turn setup into anonymous login. A crash between durable creation and handoff leaves INITIALIZING and no ordinary service access. READY databases cannot reenter bootstrap to bypass authentication; administrator recovery needs an explicit offline operator procedure.

The local Rust bootstrap API creates a previously absent data directory with owner-only access and stores `storage.redb`, a persistent setup marker, and an advisory instance lock there. Resume and normal open require that directory profile and acquire the same nonblocking exclusive lock. Resume may also claim an owner-only empty directory, or one containing only the lock file, when a crash interrupted setup before the marker was written. Initialization writes the complete built-in catalog, one LOGIN user, its membership in `database_admin`, and the first verifier in one immediate-durability redb transaction. The caller supplies the initial user name and a future token expiry; names use lowercase ASCII letters, digits, and underscores, start with a letter or underscore, and cannot equal the reserved `database_admin` name. The bootstrap session retains the lock and database handle. `bind_setup_listener` creates `.prdb-setup.sock` in the private directory with mode 0600 and accepts one connection. On Linux, the peer UID must match the directory owner. That OS check only limits access to the local setup socket; database identity still comes from the issued bearer token.

The server sends one IPC v1 frame with operation `0x0101`, a random nonzero request ID, and a 48-byte payload containing the 16-byte token ID followed by the 32-byte secret. The client sends operation `0x0102`, the same request ID, and an empty payload only after taking custody of the secret. Setup reads and writes have a 60-second timeout after connection. The server removes the socket and syncs the directory before it publishes READY. A disconnect, malformed acknowledgement, or timeout leaves INITIALIZING; resume validates that image, revokes its active bootstrap credential, and atomically issues a replacement before returning a new session. Normal open accepts READY only. The Linux x86_64 `prdb-init` utility drives this local handoff and stores the token in the canonical mode-0600 client credential file without printing the secret. A credential written before an acknowledgement error must be treated as unconfirmed and removed before retrying with `--resume`. Automated supervisor startup and broader operator recovery tooling remain separate work.

## Startup and Recovery

1. Obtain the exclusive instance lock, validate the managed directory, and open redb through its supported recovery path. redb owns physical recovery and may update its private file state while opening.
2. Read engine metadata from the recovered database and reject unsupported logical versions or lifecycle states before any engine-authored durable repair, cache rebuild, or catalog mutation. The engine cannot inspect logical metadata before redb opens because that metadata is stored in redb.
3. Validate required engine tables and catalog state. Rebuild only disposable derived indexes, and only after the compatibility and lifecycle gates pass.
4. Check mandatory built-ins, catalog references/indexes, credential verifier formats, and commit/outcome consistency. The current credential profile is SHA-256 algorithm 1, profile version 1, for uniformly random 256-bit bearer secrets. New verifier writes use that profile; startup and commit validation reject unknown algorithms or profile versions and malformed records.
5. Publish a recovered committed frontier and enable admission only after validation.

The current logical catalog schema version is 2; version-1 databases are rejected pending an offline migration path. The record-integrity pass runs against one pinned redb read transaction. It requires all versioned engine tables and exactly one `engine_meta_v1/format` record, rejects unsupported logical versions and non-READY lifecycle state, bounds catalog-family scans, and validates CAT1/EIR1 records, RWR1 row keys/versions and schema-aware TUP1 payloads against current table schemas, index definitions, bidirectional `indexes_v1`/`row_indexes_v1` membership with locator versions equal to current row versions, OUT1 outcome keys/frontiers, and AUD1 key identity. It requires exactly one family 1 database record whose key identifies the metadata database UUID and whose catalog, expression, and built-in semantics versions agree with engine metadata. Its built-in mapping must contain exactly the required 31 sorted codes, each mapped to a distinct nonzero ID with zero reserved bytes. Codes 1 and 2 must resolve to schema records and schema objects; code 3 must resolve to the `database_admin` role principal and object; codes 101–111 must resolve to primitive type records with matching `builtin_kind`, the parameter rule, encoding, comparison, default-mask, and cast-profile values assigned to that built-in kind, and type objects. Codes 201–217 remain opaque storage-object IDs because the catalog currently has no target records for them. Dependency records must resolve their dependent endpoint to a family 2 object; the referenced endpoint must also be a family 2 object except for kind-5 database-scoped system-grant edges to the family 1 database ID. Owned-child (kind 1) edges must exactly match child parent IDs and form an acyclic graph. Kind-2 edges must exactly match expression and typed schema references. Kind-3 edges must exactly match each FK constraint's referenced constraint ID and connect FK constraints to PRIMARY KEY or UNIQUE constraints. Kind-4 edges must exactly match PK/UNIQUE backing-index IDs and index owning-constraint IDs. Kind-5 edges must exactly match membership, grant, and policy-recipient authority pairs. Unknown edge kinds fail closed. Every object owner ID must resolve to an existing family 10 user or role. The family 2 object set and typed-record set must match in both directions: each object kind 1–10 has exactly one same-ID record in its corresponding typed family, and each typed row has a matching object kind. Family 10 principal kinds map to object kinds 8/9. Column and principal normalized-name bytes must match their object records. Policy column targets must resolve to family 6 columns on the policy's cell-policy table. Every constraint must resolve its table and source columns to matching typed records/object kinds, source columns must belong to that table, and NOT NULL must name a non-nullable column. Each FK must resolve its referenced constraint to a PRIMARY KEY or UNIQUE constraint, and its ordered `referenced_columns` must equal that target constraint's ordered `source_columns`. Every index must resolve its table and ordered columns to matching typed records/object kinds, and all index columns must belong to that table. Object kinds outside 1–10 fail. The pass also validates nonzero principal authority epochs and role login state, then checks that membership members, role targets, and grantors exist, targets are roles, membership epochs are nonzero, and the complete graph is acyclic and within its edge bound. Passing this pass is necessary but not sufficient for admission: storage-object ownership semantics for codes 201–217, remaining catalog references, populated cross-version fixtures, and authenticated setup/admission must also pass.

Family-17 identity tombstones are immutable. A tombstoned identity ID cannot coexist with a family-2 object or family-10 principal. Family-16 verifier rows may refer to a tombstoned user only when revoked; live credentials require a login-enabled family-10 user.

Startup also checks FK action/match/state values and requires identical built-in scalar types, including declared parameters, on each ordered column pair. After index membership validation, it verifies every non-NULL persisted source tuple against the referenced unique index; NULL source tuples follow MATCH SIMPLE. The initial implementation accepts at most 256 FK constraints and bounds combined child-row visits to 65,536. Invalid references or exceeding either bound keeps the database unavailable.

Catalog commits apply owned-child parent/edge agreement and parent-cycle validation to the final catalog whenever objects or dependency rows change. They validate kind-2 and kind-5 edge sets against final typed records, require each policy column target to resolve to a family 6 column on its cell policy's family 5 table, validate kind-3 FK target and kind-4 backing-index edges against final constraint/index definitions, and require every index table and ordered column reference to resolve to the matching table/column records and object kinds. They also require the final family 1 descriptor's codes 1–3 and 101–111 to retain the schema, `database_admin` principal/object, and matching primitive type/object targets described above, including each mapped type's specified profile values. For every object ID changed by a family 2 or typed-row write, the final view must contain both the correct object and its corresponding typed row, or neither. When objects or principals change, commits also validate every surviving object owner against the final user/role set. They apply the same typed-row/object ID and kind rule to each affected ID in families 3–10 and 13. When an object, column, or principal changes, the commit also requires matching normalized-name bytes for surviving column/principal rows. These checks resolve the transaction's final catalog view, allowing related rows to be created or removed together and rejecting mismatches atomically.

Do not silently repair missing privileges, reconstruct users with default credentials, or discard committed catalog changes to start successfully. Unsupported or corrupt databases stay unavailable with bounded operator diagnostics that contain no secrets. Read-only inspection/recovery tools also need a supported decoder and exclusive/offline access where appropriate.

## Version Domains

Persist independent versions for redb's file format, logical catalog schema, expression/policy IR, credential verifier algorithms, and built-in semantics. Engine metadata currently gates catalog schema, expression IR, and built-in semantics; each family-16 verifier records its algorithm and profile version. redb owns its physical file version and compatibility checks. Distinguish these from SDK release, host ABI, IPC, and physical-plan versions. Compatibility is explicit; a newer application version is not automatically a compatible database reader. The engine does not edit redb headers or checkpoint metadata.

Unknown mandatory record types/fields or unsupported required flags fail closed. Unknown optional fields may be skipped only where that format version defines safe length-delimited skipping. Checksums detect accidental corruption, not malicious tampering. Bind roots/logs to the database UUID to reject accidental mixing.

## Upgrade Baseline

Initial upgrades are offline. Stop admission, drain or explicitly abort active invocations, complete recovery, and take exclusive ownership. Require an independently verified backup or preserved source generation before destructive conversion. No automatic migration during a normal server start.

`prdb-maintain backup --instance-dir PATH --output-dir PATH` copies the recovered READY source image while holding the source instance's exclusive lock. It closes the validated redb handle while retaining that lock before copying, so redb's clean-shutdown allocator state is included. The destination must not exist and must be outside the source directory. It contains the private bootstrap marker and `storage.redb`, both mode 0600, in a mode-0700 directory; the source lock is not copied. Read-only validation creates a fresh empty mode-0600 instance lock in the destination. The tool syncs the copied files and directory, opens the copy through read-only READY validation, and only then publishes the adjacent `<output-dir-name>.prdb-backup` manifest with mode 0600 and a synced parent directory. The canonical UTF-8 `PRDB-BACKUP-1` manifest records the byte length and lowercase SHA-256 digest of the bootstrap marker and database file. `prdb-maintain backup-verify --backup-dir PATH` requires the manifest and lock file, compares both file lengths and digests, and opens the backup through read-only READY validation without rebuilding disposable indexes or writing to the redb file. It does not modify either directory. A backup without a valid manifest is incomplete and must not be used as a migration source. The manifest detects accidental changes; it is not an authenticity signature, so protect the backup directory and adjacent manifest with the same OS-account controls as the source. A backup duplicates database identity and credentials: do not run the copy concurrently with its source. This command creates a retained source copy; it does not restore, migrate, or select a rollback generation.

`prdb-maintain inspect --instance-dir PATH` acquires the exclusive instance lock, opens redb read-only, and performs the READY integrity validation without rebuilding disposable indexes. It prints one bounded line with the database ID, supported logical version fields, committed sequence, and validated counts for catalog records, rows, indexes, outcomes, and audit events. It does not print credential material or modify the database image. Unsupported versions, incomplete bootstrap, corruption, or an active owner produce a bounded error and no partial counts.

For each supported version transition, ship trusted Rust migration code, source/target version declarations, validation routines, and deterministic test fixtures. Migrations cannot execute SQL functions or native code supplied by database users. Preserve object/principal IDs, grant semantics, committed data, and token verifier behavior unless the migration explicitly declares a supported change.

Version 1 has no family-17 identity tombstones. A v1-to-v2 transition must preserve every previously deleted user and role ID that permanent reservations protect. The bounded and explicitly prunable AUD1 history cannot prove that set is complete, so a migration must not infer tombstones from the current audit table or silently omit them. Keep v1-to-v2 unsupported until the migration has a trusted, complete source for those IDs or a separately specified safe transition contract.

redb owns physical file format and recovery. A logical engine migration must use the pinned redb API and leave redb-private pages, headers, and checkpoint metadata untouched. Build the target in a separate `storage.redb` image at the fixed private staging name `.prdb-migration.next` in the same managed instance directory. Keep the active source at `storage.redb`; both files must be owner-owned mode-0600 regular files, and the instance lock remains held throughout conversion and publication. A migration with multiple durable batches records bounded progress in the target image; a migration that fits one redb transaction may use that transaction as its progress boundary. Never open the staging image for service admission.

After the source backup is independently verified, convert the target with trusted bounded Rust code, run full read-only READY validation against it, and cleanly close all redb handles. The target must retain the source database ID and committed sequence. Sync both closed database files, publish with one Linux `renameat2(RENAME_EXCHANGE)` between `storage.redb` and `.prdb-migration.next`, then sync the instance directory before reporting success. The exchange is the path-level root switch: after it, `storage.redb` names the validated target and `.prdb-migration.next` retains the prior source. If the filesystem does not support the atomic exchange, fail before publication; never emulate it with two renames. Managed-directory validation permits only this exact private sidecar name in addition to the existing instance files, and startup opens only `storage.redb`.

Before the exchange, restart may resume a validated migration target or discard only `.prdb-migration.next`; `storage.redb` remains authoritative. After the exchange, startup uses the target. Keep the prior source sidecar through the documented verification/rollback window; it is evidence for explicit recovery, not an automatic rollback target. After writes commit to the new generation, reverting the names would lose accepted writes and is forbidden. A process interruption during or before directory sync requires offline inspection and validation of both named images before an operator chooses recovery. `prdb-maintain migration-inspect --instance-dir PATH` holds the exclusive instance lock, validates the active READY image and any private staging image through read-only redb opens, and reports their logical versions and commit frontiers. For a staged image it reports whether the database IDs differ and which image has the later commit sequence. It accepts current v2 READY images and the exact v1 READY catalog format as offline migration sources; v1 remains unavailable for service startup. The command makes no recovery choice and does not modify either image. Never infer publication from a lost CLI reply.

Rollback before publication may discard the target. After accepting writes in the new format, pointing at the old generation would lose those writes and is forbidden as an automatic rollback. Recovery must use a supported reverse migration or an explicit backup restore with acknowledged data-loss boundaries. Never let an older binary write an upgraded directory.

## Cache and Artifact Compatibility

Restart clears ephemeral metadata caches. Durable derived statistics carry source schema/format validity and may be invalidated rather than migrated. Recompile stored typed expressions from validated canonical definitions only through trusted engine code; reject definitions that cannot preserve semantics. Existing client artifacts are admitted only if their independent ABI/protocol/plan compatibility still holds; changing the catalog does not grant old artifacts new authority.

## Tests and Remaining Choices

Exercise every initialization interruption point, lost credential handoff, duplicate initialization, redb open/recovery errors, unknown engine versions, redb upgrade compatibility, old-binary rejection, and preservation of policy semantics. Version fixtures must include populated data and multiple identities, not just empty catalogs.

The [redb backend](redb-storage.md) owns physical format compatibility and crash recovery. [Catalog payloads](catalog-payloads.md) and engine metadata have independent logical versions. Pin an exact redb release and validate its supported upgrade path. Executable fixtures, expression IR and verifier profiles, outcome/audit schemas, supported migration graph, and offline administrator recovery commands remain separate work. Their absence must block claims of an upgrade-safe release, not justify permissive startup behavior.
