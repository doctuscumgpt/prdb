# Administrative SQL Input for `prdb-client`

## Purpose and Boundary

`prdb-client admin-sql` reads one bounded SQL statement from a local file or standard input, validates the supported administrative grammar, resolves any required metadata through authenticated control APIs, and sends only typed operations over the control channel. SQL text is not sent to the gateway, and administrative SQL does not execute as a query artifact or user invocation.

## Administrative DDL Input

CHECK and policy expression SQL accepts `boolean_expression IS [NOT] TRUE`, `FALSE`, or `UNKNOWN`. Operands may be parenthesized Boolean expressions and must bind to BOOLEAN; policy-context expressions are accepted only in policy SQL. Binding lowers tests to the existing EIR1 representation. `IS TRUE`/`IS FALSE` produce false for NULL; `IS UNKNOWN` matches NULL. Unsupported truth-test names and non-BOOLEAN operands are rejected before submission.

`CREATE TABLE` name binding exposes a schema name to an effective schema-scoped `CREATE` grantee without schema `USAGE`; this metadata read does not expose the schema's existing relations or columns. The table is still created through the typed control operation, which rechecks current authority.

`prdb-client constraint-list --address IP:PORT --credentials ADMIN_FILE --schema-id HEX --table-id HEX` returns all authenticated constraint metadata for the table as one JSON array. It follows the bounded metadata pages of 128 records on one authenticated control connection, so continuation tokens remain connection-local and are not exposed as CLI cursors. Each record exposes the catalog object `name`, stable `constraint_id`, constraint `kind`, ordered `column_ids`, and (for discoverable foreign keys) the referenced table and ordered column IDs. CHECK expressions and hidden target details are omitted. Generated IDs remain supported with `ALTER TABLE schema.table DROP CONSTRAINT 'generated-id'`; any explicitly named PRIMARY KEY, UNIQUE, CHECK, or FOREIGN KEY constraint can be dropped by name.

`prdb-client index-list --address IP:PORT --credentials ADMIN_FILE --schema-id HEX --table-id HEX` returns all authenticated logical index metadata for the table as one JSON array. It follows the bounded metadata pages of 128 records on one authenticated control connection. Each record exposes `index_id`, `name`, ordered `column_ids`, and `unique`; physical storage IDs, roots, membership entries, counts, and key samples are omitted.

`prdb-client grant-list --address IP:PORT --credentials ADMIN_FILE --schema-id HEX --table-id HEX` returns the direct grants on an authorized table as one JSON array, following bounded pages on the same authenticated control connection. Each record exposes `grantee_id`, `grantor_id`, privilege, object/column target scope, and target ID. It does not expand role inheritance or reveal principal names. The server permits the read only to the schema owner or a database administrator.

`prdb-client policy-list --address IP:PORT --credentials ADMIN_FILE --schema-id HEX --table-id HEX` returns bounded policy summaries for an authorized table as one JSON array. Records expose policy ID, row/cell kind, operation, allow/restrict effect, target column IDs, and recipients only when the authenticated metadata API permits them. Policy expression IDs and bodies are never returned; recipient IDs are redacted for schema owners when required by the API.

`prdb-client admin-sql --address IP:PORT --credentials ADMIN_FILE --sql-file FILE|-` executes bounded administrative SQL through authenticated control mode. It accepts one `CREATE USER [IF NOT EXISTS] name LOGIN|NOLOGIN`, `CREATE ROLE [IF NOT EXISTS] name`, `ALTER USER|ROLE old_name RENAME TO new_name`, `DROP USER|ROLE name RESTRICT` or `DROP USER|ROLE IF EXISTS name RESTRICT`, `CREATE [UNIQUE] INDEX [IF NOT EXISTS] name ON schema.table [USING BTREE] (column, ...)`, `REBUILD INDEX schema.name`, `ALTER INDEX schema.name REBUILD [USING BTREE] {UNIQUE|NONUNIQUE} (column, ...)`, `ALTER INDEX schema.name RENAME TO new_name`, `DROP INDEX schema.name RESTRICT` or `DROP INDEX IF EXISTS schema.name RESTRICT`, or `CREATE TABLE [IF NOT EXISTS]` statement; `CREATE SCHEMA [IF NOT EXISTS] name` with optional `AUTHORIZATION owner_name|USER owner_name|ROLE owner_name|'uuid'`; `ALTER SCHEMA name RENAME TO new_name`; `ALTER SCHEMA name OWNER TO owner_name|USER owner_name|ROLE owner_name`; `DROP SCHEMA name RESTRICT` or `DROP SCHEMA IF EXISTS name RESTRICT`; bounded `CREATE ROW|CELL POLICY`, `DROP ROW|CELL POLICY`, and `DROP ROW|CELL POLICY IF EXISTS` statements as specified in [permission DDL](ddl-permissions.md); `ALTER TABLE schema.table RENAME TO new_name`; `ALTER TABLE schema.table OWNER TO USER|ROLE owner_name`; `ALTER TABLE schema.table ADD [CONSTRAINT name] PRIMARY KEY (column, ...)`; `ALTER TABLE schema.table ADD [CONSTRAINT name] UNIQUE (column, ...)`; `ALTER TABLE schema.table ADD [CONSTRAINT name] CHECK (expression)`; `ALTER TABLE schema.table ALTER COLUMN column SET NOT NULL`; `ALTER TABLE schema.table ALTER COLUMN column DROP NOT NULL`; `ALTER TABLE schema.table ALTER COLUMN column SET DEFAULT literal`; `ALTER TABLE schema.table ALTER COLUMN column DROP DEFAULT`; `ALTER TABLE schema.table ADD COLUMN [IF NOT EXISTS] column type [NOT NULL] [DEFAULT literal]`; `ALTER TABLE schema.table RENAME COLUMN old_name TO new_name`; `ALTER TABLE schema.table DROP COLUMN column RESTRICT` or `ALTER TABLE schema.table DROP COLUMN IF EXISTS column RESTRICT`; or `DROP TABLE schema.table RESTRICT` or `DROP TABLE IF EXISTS schema.table RESTRICT`. For conditional identity, table, schema, index, policy, or column drops, an unresolved target is a successful no-op only for a database administrator; a resolved object goes through its normal authorization and RESTRICT checks. Other failures are not suppressed. For `CREATE USER|ROLE IF NOT EXISTS`, a requested-kind identity that already exists is a database-administrator-only no-op with no DDL outcome and no login-state change; an absent identity follows normal typed creation and authorization. CREATE USER accepts explicit LOGIN or NOLOGIN and never issues a credential; token issuance remains a separate control operation. CREATE ROLE creates a permission group. Both use the corresponding authenticated typed identity operation. CREATE INDEX resolves the schema, table, and ordered columns through authenticated metadata before dispatching the existing typed index-create operation; storage enforces DDL authority, uniqueness, and catalog invariants. `CREATE INDEX IF NOT EXISTS` creates an absent index normally; a resolved existing index is a database-administrator-only no-op with no DDL outcome and no definition reconciliation. REBUILD INDEX and DROP INDEX resolve an unambiguous logical index name among administratively visible tables in the named schema, then dispatch the existing typed operation using the authenticated index ID. REBUILD INDEX carries the current ordered column IDs and uniqueness flag from metadata; storage validates and republishes memberships atomically, including when the definition is unchanged. ALTER INDEX REBUILD also resolves the owning table and binds the requested new ordered columns through authenticated metadata before dispatching `indexes.rebuild` with the explicit UNIQUE/NONUNIQUE profile. Storage validates and publishes the changed definition and memberships atomically. `ALTER INDEX schema.name RENAME TO new_name` resolves the index by authenticated metadata and renames its logical catalog object without rebuilding physical memberships; ordinary index DDL authorization and schema-level name uniqueness still apply. DROP INDEX requires explicit RESTRICT. Duplicate or unavailable names reject before mutation. It reads at most 65,536 UTF-8 bytes without NUL and rejects malformed or unsupported syntax before reading credentials or connecting. Schema ownership defaults to the authenticated principal or may be supplied as a hexadecimal UUID (with or without hyphens), a `USER` name, or a `ROLE` name; named identities are resolved through authenticated metadata, and storage validates the owner and caller authority. `CREATE SCHEMA IF NOT EXISTS` creates an absent schema through the normal typed authorization path; an existing schema is a no-op only for a database administrator and commits no DDL outcome. Schema-scoped `ALTER` grantees can resolve the schema name needed by `ALTER SCHEMA` without schema `USAGE`; this does not expose relations or columns. Table-scoped `ALTER` grantees can resolve the table metadata needed by supported table DDL without data grants or schema `USAGE`. Schema and table owner-transfer SQL resolve destination names through authenticated metadata scoped to the target schema/table owner or effective ALTER authority; untyped schema-owner names use the globally unique principal-name index. Other DDL resolves target metadata before mutation. Policy creation resolves table, recipients, columns, and `HAS_ROLE` names through authenticated metadata before binding the predicate and dispatching the typed policy operation. Each statement maps to its corresponding typed control operation. SQL text is not sent to the gateway. On success the command prints operation/commit metadata and generated IDs when applicable. It does not use query artifacts or user invocation transactions. The CREATE TABLE grammar supports `CREATE TABLE [IF NOT EXISTS]` with scalar columns, optional NOT NULL, `UUID GENERATED ALWAYS AS IDENTITY` (implies NOT NULL and excludes DEFAULT), and the typed DEFAULT forms listed in [schema DDL](ddl-schema.md). Final table-level `PRIMARY KEY (column, ...)`, `UNIQUE (column, ...)`, `[CONSTRAINT name] CHECK (expression)`, and `FOREIGN KEY (columns...) REFERENCES target_schema.target_table (columns...)` clauses are optional; at most one primary key is accepted, and distinct unique, CHECK, and FK constraints are supported. Primary-key columns imply NOT NULL. Keys, owned unique indexes, CHECK expressions, FK dependencies, referenced-table write epochs, and the new table publish atomically; nullable UNIQUE tuples remain distinct. An external CREATE TABLE FK resolves its existing target through authenticated metadata, requires ordered visible PRIMARY KEY or UNIQUE columns with identical source types, and requires REFERENCES authority. CREATE TABLE CHECK accepts Boolean column references, `IS [NOT] NULL` on supported scalar expressions, `NOT`, `AND`, `OR`, parentheses, and `=`, `!=`, `<>`, `<`, `<=`, `>`, and `>=` comparisons. `IS [NOT] DISTINCT FROM` accepts a supported scalar expression on each side, including expressions that evaluate to NULL. `IN`/`NOT IN` accepts one to 64 supported scalar expressions, and `BETWEEN`/`NOT BETWEEN` accepts two supported scalar expressions as bounds; both predicates apply to any supported scalar expression. Comparisons accept supported scalar expressions on both sides and contextually parse literals as the opposite operand type, including boolean, signed integer, exact DECIMAL, quoted text/VARCHAR/UUID, `X'hex'` BYTEA, engine-epoch DATE/TIMESTAMPTZ integer, and SQL NULL. Type mismatches and lossy DECIMAL rescaling are rejected before PREPARE. For `CREATE TABLE IF NOT EXISTS`, an absent relation follows normal typed creation, while a resolved existing relation is a database-administrator-only no-op with no DDL outcome; the existing definition is not compared or reconciled. Storage remains responsible for generating identity values during INSERT and rejecting overrides. Column-level PRIMARY KEY, UNIQUE, and CHECK constraints are supported; a column-level CHECK may reference only its declared column. Column-level `REFERENCES schema.table (column)` creates a one-column foreign key and follows the same external or same-statement self-reference rules. For a self-reference, the target key must be declared in that CREATE TABLE; the client emits a local target and storage resolves its generated IDs atomically. Named PRIMARY KEY, UNIQUE, CHECK, and FOREIGN KEY constraints are supported in column or table form where applicable, retained in metadata, and droppable by name through `ALTER TABLE ... DROP CONSTRAINT`. Quoted identifiers and multiple statements remain unsupported. The ALTER CHECK grammar supports the same bounded expression subset and typed comparisons/literals. It resolves identifiers and column types through authenticated metadata before PREPARE. A supplied ALTER CHECK name is retained on the CHECK object and can be used by DROP CONSTRAINT; duplicate names are checked in the authorized fenced catalog commit. Nullability alterations resolve the column through authenticated metadata and dispatch the typed `tables.alter_column_nullability` operation. Default changes resolve the column type and nullability through authenticated metadata, bind one typed literal, and dispatch `tables.set_column_default` or `tables.drop_column_default`; existing rows are not rewritten. ADD COLUMN resolves the table and submits one typed column definition; NOT NULL requires a type-compatible non-null literal default, and context-dependent defaults are rejected. RENAME COLUMN resolves the declared column through authenticated metadata and dispatches `tables.rename_column`. DROP COLUMN requires explicit RESTRICT, resolves the declared column through metadata, and dispatches `tables.drop_column`. `DROP COLUMN IF EXISTS` suppresses an unresolved target only after database-administrator authority is confirmed; a resolved column retains ordinary DDL and RESTRICT checks.

`CREATE ROW|CELL POLICY` uses the engine policy grammar in [permission DDL](ddl-permissions.md), with mandatory operation-specific `USING`/`WITH CHECK` clauses. The client resolves recipient and `HAS_ROLE` identities, field names, and target table through authenticated metadata, binds the supported Boolean predicate to stable IDs/ordinals, and calls `policies.create`; storage revalidates policy shape, actor authority, dependencies, and publication. Identity resolution is scoped to the schema and table and permits the table/schema owner, a scoped `MANAGE_POLICIES` grantee, or a database administrator; absent and unauthorized identities both return null. A policy DDL authority can resolve the target relation and its declared columns without data SELECT, while the caller must still have schema USAGE to resolve the schema name. Other metadata relations continue to follow existing grant visibility. `DROP ROW|CELL POLICY name ON schema.table RESTRICT` resolves one policy of the specified kind within the table using the same scoped authority, then calls `policies.drop`, which revalidates authority. `DROP ROW|CELL POLICY IF EXISTS` suppresses an unresolved target only after the server confirms database-administrator authority; a resolved policy retains regular authorization. Missing and unauthorized policies both return no ID. The client rejects unsupported functions and malformed clauses before mutation.

The command also accepts `ALTER TABLE schema.table ADD [CONSTRAINT name] FOREIGN KEY (source_columns...) REFERENCES target_schema.target_table (target_columns...)`, `ALTER TABLE schema.table DROP CONSTRAINT name|'generated-id'`, and `ALTER TABLE schema.table DROP CONSTRAINT IF EXISTS name|'generated-id'`. It resolves both relations and their ordered columns through authenticated metadata, requires the referenced columns to match a visible PRIMARY KEY or UNIQUE constraint, and uses the typed foreign-key create/drop operations. Constraint names, IDs, kinds, and source columns are visible to schema/table owners, database administrators, and effective table-scoped `ALTER` grantees; FK target details remain redacted without target-schema visibility. DROP by generated ID accepts PRIMARY KEY, UNIQUE, CHECK, or FOREIGN KEY constraints; DROP by name resolves any explicitly named PRIMARY KEY, UNIQUE, CHECK, or FOREIGN KEY constraint. The conditional form suppresses an unresolved name or ID only for a database administrator.
