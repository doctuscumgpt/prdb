# Interactive SQL Implementation Progress

## Current Status

Implementation and acceptance are complete. The normative initial profile is frozen in [`specs/interactive-sql.md`](../../specs/interactive-sql.md). Acceptance includes real CLI script execution, fresh-connection transaction reattachment, RUNAS and DDL, lost-reply reconciliation, restart recovery, actor-isolated staged writes, and confined checks that hostile query code cannot invoke transaction-control or ADMIN IPC.

- ISQL-1: v2 framing, strict transaction-control codecs, version-matched HELLO, authenticated transaction-control dispatch, v2 PREPARE/SEAL/START binding, and a typed v2 client connection are implemented. TCP tests cover BEGIN on one connection followed by ATTACH/COMMIT on another.
- ISQL-2: bounded SQL script/RUNAS parsing, secure multi-profile loading, and the prompt REPL are implemented. Script and REPL share one sequential dispatcher; multiline RUNAS input is buffered through ENDRUNAS and EOF rolls back an open transaction. The process-level CLI test exercises profiles, autocommit RUNAS, explicit-transaction RUNAS, rollback, and DDL interleaving.
- ISQL-3: the bounded SDK batch runner and mixed SELECT/INSERT/UPDATE/DELETE dispatcher are implemented. Maintained TinyCC tests pass; the confined gateway test now executes one RUNAS package containing INSERT and two SELECTs.
- ISQL-4: the storage-owned transaction registry and package-scoped supervisor handle are implemented. The confined TCP test now executes two separate RUNAS packages against one explicit MVCC transaction; the second sees rows staged by both packages, and COMMIT publishes the shared write set.
- ISQL-5: actor authentication, actor-specific authorization projection, writer attribution, actor-filtered overlays, and commit-time actor authority checks are implemented. The confined test proves an actor can INSERT and read its own staged row with explicit table/column grants and row/cell policies. A second SELECT-only actor with matching row/cell policies completes a package but receives no result rows for the first actor's private staged insert. The test also stages an actor write, revokes that actor's token, and verifies COMMIT rejects the transaction and the staged row remains absent.
- ISQL-6: v2 transaction transport, fresh-connection attach, transaction-bound package upload, actor-proof START, package-terminal decoding, and real TCP-to-confined-executor RUNAS execution are implemented. TX_BEGIN uses a controller-scoped idempotency key. The process-level response-dropping proxy covers uncertain BEGIN, autocommit START, streamed package result data, COMMIT, and ROLLBACK; package and commit outcomes are reconciled without replay.
- ISQL-7: the loopback-only `prdb-client interactive-sql` composes script/REPL dispatch, credential profiles, package build/submit, v2 transaction operations, provisional SQLB result decoding, and typed DDL. The real CLI process now runs a mixed script through a live gateway and confined executor using an admin default profile plus a restricted RUNAS profile; it performs autocommit RUNAS, explicit-transaction RUNAS and ROLLBACK, and CREATE/DROP SCHEMA around the transaction.
- ISQL-8: confined TCP acceptance compiles one SQLB package containing INSERT and two SELECTs, attaches to an explicit transaction from a fresh connection, authenticates a second RUNAS user, verifies actor read-your-own-write results, then runs a second package in the same transaction and proves it sees both packages' staged rows before COMMIT. A SELECT-only third identity sees no rows from the first actor's private overlay. The same batch runs authenticated as its actor in autocommit and reaches a durable committed terminal. A separate transaction stages another RUNAS insert, rolls back, and a later confined query confirms it is absent. Another actor stages a write, has its token revoked, and is rejected at COMMIT; a subsequent confined query confirms the row was not published. Process tests prove undecided transactions become durably ABORTED after supervisor restart and committed outcomes remain visible. Hostile C query code also attempts both interactive transaction-control and administrative executor callbacks; the confined test verifies both are denied.

## ISQL-3 One-Package SQL Batch SDK — Partial

- Implementation: `prdb_sdk_sql_run_batch_v1` accepts a pre-lexed array of SQL/parameter slices, enforces count and byte limits, wraps executor/planner/output/failure host callbacks, emits SQLB v1 START/DATA/COMPLETE/FAILED records, and stops on the first execution or output error. It does not split SQL text. `client_sql::generate_query_batch_source` uses the Rust interactive lexer to generate a query-only C wrapper from numeric byte arrays and the batch API. ## ISQL-4 Storage Transaction Registry — In Progress

- Contract: a single retained MVCC transaction spans package requests and authenticated connections; package failures make it abort-only; transaction IDs are not authority. Limits are specified in [`specs/interactive-sql.md`](../../specs/interactive-sql.md).
- Implementation: `StorageManager` clones share an in-process registry retaining one `InvocationTransaction`, including its snapshot, overlay, conflict guards, and admission permit. BEGIN authenticates the token and generates the transaction ID. ATTACH, STATUS, COMMIT, ROLLBACK, package execution, and package status authenticate the controller. The registry serializes each package callback, reserves package IDs against digest replay/conflict, clears the per-package requested-scope ceiling after each callback, marks failures abort-only, and records result loss without replaying bytes. A trusted package callback can now receive a disposable `SupervisorInvocation` sharing that exact transaction context; successful package completion leaves the transaction open for controller COMMIT, while callback error or panic marks it abort-only. Five-minute idle and configured lifetime expiration abort the transaction. A bounded supervisor maintenance pass reaps expired transactions and terminal records; terminal package status is retained through the configured outcome-retention deadline.
- Limits: 128 packages, 65,536 staged rows, 64 MiB cumulative staged writes, 64 MiB package artifact, and existing global/per-controller active invocation quotas.
- Tests: six focused integration tests pass. They verify one transaction object is reused by two packages through cloned manager handles, a disposable supervisor handle shares the context and does not commit at package end, controller authentication is required, package IDs cannot replay/conflict, simultaneous package starts reject, commit and rollback decisions are terminal, package failure aborts the transaction, result-loss status is retained, and lifetime expiry aborts/releases the transaction. Gateway tests verify v2 transaction kinds map to the gateway-only IPC operation and that executor authorization rejects it. The pointer-identity assertion proves the same context object is reused; actual row-level read-your-writes and concurrent storage isolation are not covered yet.
- Commands: `nix develop --no-update-lock-file -c cargo fmt --all -- --check` passed; `nix develop --no-update-lock-file -c cargo test -p prdb-engine --lib gateway_error_payload_tests --locked` (3 passed); `nix develop --no-update-lock-file -c cargo test -p prdb-engine --test interactive_transactions --locked` (6 passed); `nix develop --no-update-lock-file -c cargo clippy -p prdb-engine --all-targets --locked -- -D warnings` passed; `git diff --check` passed. `cargo check -p prdb-engine --locked` passed after the shared-handle refactor. The full library suite has not been rerun since the latest gateway/IPC additions.
- Implementation update: transaction-control frames 13–18 now cross the TCP gateway through a dedicated IPC operation and dispatch to the authenticated v2 session handler. The selected protocol major is carried on HELLO so v2 clients receive a v2 HELLO response. V2-only transaction kinds are rejected on v1 connections. The generated IPC ABI schema and C/Rust declarations were regenerated.
- Implementation update: protocol v2 PREPARE now accepts only the paired nonzero transaction/package IDs; v1 rejects these extension fields. Staging stores them outside artifact input and copies them into the immutable `SealedSubmission`. V2 START must echo the same pair, and the service compares it to the sealed binding. Focused codec and staging tests cover version rejection, partial/zero IDs, and binding retention.
- Implementation update: the gateway service handles a bound v2 START inline, launches and observes the disposable worker inside `execute_interactive_package_with_supervisor`, streams provisional result data, and emits a package terminal event without committing the transaction. Launch, worker, and result-relay failures fail the package and make the transaction abort-only. Direct dispatch rejects bound START so it cannot fall back to the one-shot transaction path.
- Remaining work: durable package-state recovery and broader row-level MVCC acceptance. A successful RUNAS package is now exercised through the real v2 gateway/executor path.
- Next smallest increment: independently authenticate RUNAS actors and bind their principal/role projection to each package worker.
