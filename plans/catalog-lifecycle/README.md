# Catalog Lifecycle Implementation Plan

## Contract and Dependencies

Implement [bootstrap/startup/offline upgrades](../../specs/catalog-lifecycle.md) using the pinned [redb backend](../storage-manager/README.md), [dictionary](../data-dictionary/README.md) and [credential profile](../ddl-identity/README.md). Initialization never requires SQL, SDK, optimizer or user code. Supervisor admission waits for validated READY.

## Decisions Before Implementation

The local directory profile, one-time secret handoff over a permission-restricted Unix socket, interrupted-handoff token rotation, `prdb-init` setup client, checksummed offline READY backup/verification, and read-only READY inspection are implemented. Compatibility gates reject unsupported catalog, expression, and built-in semantics versions; family-16 credential rows carry and validate an algorithm and profile version. The CL-5 path-level publication design now uses a same-directory atomic exchange of the active and staging redb filenames, leaving redb page ownership with redb. A version matrix now distinguishes service support, legacy source validation/backup, and executable transitions. Migration inspection can compare active/staged bytes to a verified backup, and unpublished staging can be discarded only when the backup proves the active source is unchanged. Catalog-v1 migration now has a bounded one-transaction record transformer and an offline `migration-apply` command that requires a verified source backup plus an explicitly acknowledged complete identity-history file. The command validates and atomically exchanges the v2 target while retaining the source generation. An explicit `restore` command can recover an unreadable active image from a verified v2 backup only with a data-loss acknowledgment; it retains the displaced file. `redb-format-upgrade` now converts a READY physical-v2 instance using a mode-0600 independent byte backup, a pinned redb 2.6.4 staging upgrade, all-table logical digest comparison, full READY validation, and atomic filename exchange that retains the source generation. Retry verifies the active image and retained v2 source against the backup. Process-exit regressions cover before and after exchange; the pre-exchange case preserves the active v2 file while retry rebuilds a completed staging target. A historical catalog-v1 runtime rejected a catalog-v2 image with `UnsupportedFormat`; its attempt changed the redb file digest, while a row-by-row digest of all 20 logical tables matched a control copy. Physical redb-v2 rejection is tested against both a small database and a populated PRDB image; a redb-2.6-upgraded populated image passes current READY validation with its application row intact. Broader power-loss evidence and remaining release acceptance are still open. Distinguish redb format, engine/catalog, policy IR, verifier and built-in semantics versions from network/ABI/plan versions.

## Increments

| ID | Observable test first | Minimum implementation and evidence |
| --- | --- | --- |
| CL-1 | Bootstrap descriptor resolves reserved records without SQL; duplicate initialization cannot replace committed identities | Minimal trusted descriptor, database UUID, tables/indexes and recoverable initialization transaction |
| CL-2 | Failure at every handoff/state boundary resumes safely without a default credential or plaintext persisted secret | Protected local first-admin/token delivery, explicit lost-delivery reconciliation and one-time verifier persistence |
| CL-3 | Unknown version, required record/index corruption or redb recovery error blocks READY | Open with pinned supported redb, validate logical tables/catalog/dependencies/authority and publish readiness only after success |
| CL-4 | An older binary/unsupported verifier or IR cannot silently read-write a newer directory | Explicit independent compatibility gates and populated cross-version fixtures; ordinary startup performs no automatic migration |
| CL-5 prerequisite | A READY source can be preserved and independently re-opened before conversion | Exclusive offline lock, private byte copy, durable checksummed manifest, read-only READY validation, and repeatable verification |
| CL-5 | Offline migration interruption before publication preserves source; after publication startup uses completed target | Stop admission/drain, exclusive access, verified backup/source generation, trusted bounded conversion and redb-supported atomic generation publication |
| CL-6 | Upgrade preserves IDs, data, grants/policies and verifier semantics; post-upgrade writes prevent unsafe automatic rollback | Validate target before switch, retain source for documented window, test reverse migration/explicit restore boundaries and rebuild disposable derived caches |

## Acceptance and Handoff

CL-1 and CL-2 bootstrap, protected one-time credential handoff, and `prdb-init` are implemented with isolated-file and process-exit regressions. CL-3 startup validates the bootstrap descriptor and catalog graph before READY. CL-4 has explicit catalog/verifier/expression/built-in compatibility gates and a tested populated physical redb-v2-to-v3 upgrade. CL-5 provides verified offline backups, bounded catalog-v1 migration, source retention, and atomic same-directory filename exchange while leaving redb-owned pages untouched. CL-6 includes explicit restore boundaries, rejection of rollback after post-upgrade writes, and migration fixtures covering IDs, credentials, grants, row/cell policies, and application rows. See [component progress](PROGRESS.md) for exact evidence and limits.

Remaining release evidence includes real power-loss/device-cache behavior, archived binaries and data directories from prior releases, and broader filesystem fault campaigns. Process-exit and injected syscall-boundary tests run with the kernel and filesystem alive and must not be presented as power-loss proof. Preserve the source generation and require explicit acknowledgments for destructive restore; never edit redb private headers, roots, or checkpoint metadata.
